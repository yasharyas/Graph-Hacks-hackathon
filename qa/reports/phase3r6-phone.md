# Patient Zero: Phase 3 round 6, phone QA (LinkedIn/X-link persona)

Target: production build `http://localhost:8080/` (the link people tap). Vite dev `http://localhost:5173/` was used only for one throttled cold load. Chromium headless via Playwright, iPhone UA, `isMobile`, `hasTouch`, DPR 2, `tap()` / `touchscreen.tap()` for taps, CDP touch events for swipes and the scrubber drag. Viewports: 375x812 (main), 390x844, 320x640, 812x375. Every flow ran in a fresh browser context (fresh session). Shots: `qa/reports/phase3r6-phone/` (file names in brackets). Scripts: scratchpad `r6phone/` (not in the repo). No repo file was edited, nothing committed, no server touched, `.env` not read.

Caveats, stated up front:
- Headless Chromium has no soft keyboard. "Keyboard up" is simulated by shrinking the layout viewport (Android resizes-content model). iOS visual-viewport behaviour is untested and WebKit was not available, so anything iOS-specific is reasoned, not observed.
- CLS: this headless Chromium flags layout shifts in the first ~500 ms after navigation as "had recent input" (it happens on plain landing loads with no input at all), so the browser's standard value hides load-time shifts. For loads and share links I therefore report the raw total as well as the standard value. After a tap, the standard value excludes the tap-triggered shift by design, so I report both there too.
- axe-core 4.x was re-run this round (CSP bypass for the injection only): 0 violations in 9 states x 2 viewports.
- Playwright's 0 ms synthetic tap was occasionally swallowed (no `click` fired) right after a CDP swipe plus Back. I treated that as an automation artifact and did not report it.
